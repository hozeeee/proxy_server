1. send 方法是否能够感知对端是否接收成功，如果不能则需要加个接收数据后的应答功能。客户端发送数据，必须要检验是否发送成功，也就是对端必须给出 ack ，感知对方是否真的收到。我提的这点需求，在业内应该有成熟的方案吧？你可以先把方案和我说说，让我看看是否符合我预期。
2. 消息发送失败应该有重试。可以给客户端启动增加参数，是否不重发数据，默认开启。
3. 重发数据可能会有个隐含问题，例如数据其实是发送成功，但 ack 却发送失败，可能会导致数据重复发送，方案设计注意这种情况的处理。
4. 如果发送数据连续五次(可参数配置)发送失败，那判定为通道已经出问题，应该重新建立。此功能的实现可以结合服务端，例如发送通知给服务端，然后让服务端发送只能让两个客户端重新建立连接。既然做了这个功能，也可以在页面上补充该功能，点一下就让对应的两个客户端重新走通道建立的流程。
5. 在原本客户端建立连接成功后的基础上，加上这么一个功能，双发都给对方连续发送三份数据包，(注意要有一定发送间隔，发送次数和间隔都可以通过启动参数配置)，只有数据有应答才算建立成功。如果数据都没有发送成功，那就应该通知服务端，让对方重新建立连接。
6. 如果前面提到的"假成功"是 answerer 或 initiator 端的小部分代码问题，处理即可修复，那上面[5]的功能可以不做。
